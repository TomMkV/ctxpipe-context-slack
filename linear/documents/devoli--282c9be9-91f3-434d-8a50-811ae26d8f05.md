# Devoli

[Devoli ](<https://devoli.com/>)is **a New Zealand-based, independent telecommunications wholesaler** that operates across Australia and New Zealand, providing automated internet, voice, and data services. As a major infrastructure provider supporting over 115,000 households and businesses, they specialize in white-label solutions, allowing MSPs and ISPs to manage services via their platform

## Tom's notes (Granola)

**Current Architecture & Agent Challenges**

* Legacy monolith with 260 repos (many inactive/archivable)
  * Target: \~10 relevant repos in microservices architecture
  * PHP(?) monolith missing fundamental business concepts
  * Moving to domain models with customer/supplier interface layers
* Agent context quality critical for success
  * Volume of context less important than relevance
  * Agents going off-track without proper guidance
  * Need organisational story (what was/is/will be) to prevent old pattern adoption

**Current Agent Workflow & Tools**

* Feature development process:
  1. Mixed across team
  2. Start of a governance/pattern repo (by Robin)
  3. Some provide JIRA ticket as starting point
  4. Interactive planning and direction with agent in Claude / Opencode / Cursor
  5. Generate PRs with infrequent Copilot review, based on complexity of feature/work
* Selective application to smaller, well-understood features (1-2 repos)
* Experimenting with upstream tasks (product analysis, architectural planning) more and more with AI in the IDE
* Documentation scattered across:
  * JIRA (product backlog)
  * GitHub (code, PRs)
  * Confluence (internal knowledge, varying quality/currency)
  * Zendesk (customer docs, no access)
* Infrastructure: CDK for new deployments, legacy hand-cranked AWS

**Implementation & Next Steps**

* Self-hosted deployment preferred (security/access requirements)
* Technical requirements:
  * Fargate ECS deployment
  * CDK infrastructure as code
  * Bedrock integration needed (AWS-specific auth)
  * Postgres (Aurora), Neptune graph DB, S3/EBS storage
* Timeline: 1-2 weeks for valuable functionality
* Slack channel for ongoing communication (for us to set up)
* Need to introduce a proactive means to prompt users to guide system

# June 30th 2026 - Kick off meeting

### **Customer Context and Pain Points**

* Robin’s company has ~260 repos (active ones around that number, long tail beyond)
* Distributed system: bounded contexts across orders, subscriptions, customers, products
* External integrations are messy: range from web scraping to clean JSON APIs
* Core pain: assessing impact and risk of a feature change across disconnected repos
  * Current approach: grep across locally checked-out repos, doesn’t scale
* Architecture is evolving: strong principles in newer services, legacy is inconsistent
  * Goal: formalized interface specs, but not there yet

**Deployment and Access**

* Robin’s team is on AWS: CDK is the recommended deployment path
* Plan to spin up in an isolated AWS account (separate from production domains)
  * Context Pipes doesn’t talk to internal services directly, only to Git providers and model providers
* Access control options: VPN in front, or built-in login/registration
* Onboarding flow: connect GitHub app, select repos to ingest, add Confluence connector if needed
