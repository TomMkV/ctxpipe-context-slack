# CTX-14: User's can see each others conversations

In the TruRecAI org, user Progyan can see user Byron's conversations in the chat UI list in TruRecAI

It seemed to trigger on Progyan deleting a conversation - it was replaced with someone else's (Byron's).

## What I changed

Conversations were keyed only by **organisation**, so every member saw the same list. I added `user_id` (Better Auth user id, FK to `users`) and wired **every** conversation path through `org_id` + `user_id`: list (paginated), get, patch, delete, `touchConversationLastMessage`, and `ensureConversation`. The REST schema now returns `userId` on each conversation.

The UI was also caching by `orgSlug` only, which could show another account’s list after sign-out/sign-in on the same browser profile. Query keys now include `session.user.id`, and optimistic list items carry that id.

**PR:** [https://github.com/ctxpipe-ai/ctxpipe/pull/92](<https://github.com/ctxpipe-ai/ctxpipe/pull/92>)

Branch: `cursor/conversation-user-scope-0507`

## Migration behaviour (important)

The migration adds `user_id`, backfills **only** for orgs with **exactly one** member, then **deletes** any row still missing `user_id` (typical multi-member orgs with old shared rows). That is deliberate: guessing an owner for shared legacy rows would be **worse** than dropping them. Upside: no more cross-user visibility. Downside: some orgs may lose **unscoped** historical chat metadata until people start new threads (graph checkpoints keyed by thread id are unchanged; only the Postgres row may be gone).

## Caveats

* I could not run `pnpm run db:generate` here: Drizzle Kit wanted an interactive TTY for index rename vs create. The SQL migration was written to match the schema; your team may want to run `db:generate` locally once to refresh Drizzle metadata if your workflow depends on it.
* Full backend `vitest` / `tsc` already fail on unrelated files in this environment; I ran `vitest run src/mcp/tools.test.ts` and **Biome** on the files touched.

If you want **zero** data loss for multi-member orgs, the migration would need a different rule (e.g. explicit admin mapping or a one-off script)—happy to discuss trade-offs.

Here is a concise analysis grounded in how this repo actually works.

## Most plausible explanation (matches “after delete I saw someone else’s chat”)

**Conversation rows are scoped to the organisation only, not to the signed-in user.** The list endpoint loads every conversation for the current org (optionally filtered by `source`), ordered by recency. There is no `userId` / owner column on `conversations`.

```3:25:apps/backend/src/db/schema/conversations.ts

  "conversations",
  {
    id: text("id").primaryKey(),
    orgId: text("org_id").notNull(),
    name: text("name").notNull().default("New Chat"),
    source: text("source"),
    lastMessageAt: timestamp("last_message_at", {
      withTimezone: true,
      mode: "date",
    }),
    // ...
  },
  (t) => [
    index().on(t.orgId, t.lastMessageAt),
    // ...
  ],
)
```

```73:98:apps/backend/src/models/conversations.ts
export async function listConversations(input?: {
  source?: string
}): Promise<ConversationRecord[]> {
  const orgId = requireCurrentOrgId()
  const db = getOrgDb()
  if (input?.source) {
    return db.query.conversations.findMany({
      where: {
        orgId: { eq: orgId },
        source: { eq: input.source },
      },
      // ...
    })
  }
  return db.query.conversations.findMany({
    where: { orgId: { eq: orgId } },
    // ...
  })
}
```

So in **TruRecAI**, Progyan and Byron are in the same org: **both are meant to receive the same list from the API**. After Progyan deletes one row, the client refetches (`invalidateQueries` on delete success in `ConversationList.tsx`), the window shifts, and the “next” conversation in that shared list can easily be Byron’s. That can feel like “my row was replaced by someone else’s” even though the behaviour is “org-wide inbox,” not cross-account leakage in the sense of wrong `orgId`.

**Critical implication:** If the product expectation is *private chats per user within an org*, the current schema and queries do not implement that; the issue may be **missing user-level tenancy**, not a one-off UI glitch.

---

## Other plausible (weaker) angles

1. **Message bodies are also keyed only by conversation id in the graph layer** (`thread_id: input.conversationId` in `transport.ts`). If there were ever **ID reuse or collision** across users, two people could theoretically attach to the same thread. That is a long shot if IDs are proper unique strings; the org-wide list is the much simpler reading.
2. **Stale or wrong org context** (e.g. session still tied to another org, or a bug in `requireCurrentOrgId()` / route param mismatch) could show another org’s conversations. That would be a real auth bug. I did not see evidence of that in the snippets above; the default reading for same-org users is still the org-wide list.
3. **Shared browser profile / shared machine** could present as “I see their chats” without any server defect.

---

## How I’d validate before changing code

* Confirm whether **private per-user** chats are a requirement for orgs like TruRecAI. If yes, the fix is **model + API**: add ownership (or membership) and filter list/get/delete/stream by that, not only `orgId`.
* Reproduce: two users in the same org, each creates chats, A deletes one → **API response** for `GET .../conversations` should already include B’s rows today.

I have not changed any code because your message asked for **potential reasons**; the strongest one is **org-level conversation visibility by design**, with delete + refetch making another member’s row visible for the first time in that viewport.
