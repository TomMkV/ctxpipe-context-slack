## What was going wrong

Two separate mechanisms were in play:

1. **Web app (cookies + DB session)** — Better Auth’s defaults are a **7-day** session with a **1-day** sliding refresh (`updateAge`). That alone does not explain “a few hours” unless something else was shortening perceived auth.
2. **MCP (**`/mcp` with `Authorization: Bearer`) — `withBearerAuth` verifies a **JWT** whose expiry comes from the **OAuth provider access token**, which defaults to `accessTokenExpiresIn` = 3600 seconds (1 hour) in `@better-auth/oauth-provider`. So MCP clients could look “flaky” or drop while the browser session still felt fine: the **bearer JWT expired hourly** even when the underlying session row lived longer.

So yes: **MCP flakiness can be tied to session/token lifetime**, but specifically to **OAuth access-token JWT lifetime**, not only “inactivity” on the web app.

## What I changed

In `apps/backend/src/auth/config.ts`:

* `session`: `expiresIn: 30 days`, `updateAge: 24 hours` — longer-lived browser sessions with a once-per-day sliding extension when the session is used.
* `oauthProvider`: `accessTokenExpiresIn: 7 days` — JWTs used for Bearer MCP auth align with a multi-day window instead of the previous **1-hour** default.

Draft PR: [https://github.com/ctxpipe-ai/ctxpipe/pull/84](<https://github.com/ctxpipe-ai/ctxpipe/pull/84>)

**Security caveat (worth stating plainly):** longer-lived bearer tokens increase blast radius if leaked. If your threat model prefers shorter MCP tokens, shorten `OAUTH_ACCESS_TOKEN_EXPIRES_IN_SECONDS` or implement refresh in the MCP client instead of stretching `exp` this far.

**“Remember me”:** Better Auth already supports persistent vs session-only cookies; the UI uses `@daveyplate/better-auth-ui`’s `AuthView`, which can expose that if enabled upstream. This change focuses on the **server-side TTLs** that were clearly misaligned (especially for MCP).
