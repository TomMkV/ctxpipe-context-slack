# CTX-39: Add 'data processing' page to the docs

We need to better respond to how data is processed in ctx|, in addition to what controls the user has. We also should list subprocessors.

Here is a draft of the page. for now, this page should be specific to the Docs, and not (currently hidden) Self Hosting section of the docs.

Draft:

---

# Data & Privacy

## What ctx| ingests

* ctx| only ingests from Git
* All sources (including future integrations like Confluence) are synced to Git before ingestion
* What's in your connected repos is what ctx| can see — nothing more

## What you control

* You connect repos explicitly through the web UI
* Nothing is ingested without your action
* You can remove repos at any time
* Ingested data is scoped to your organisation — other tenants cannot access it

## Sub-processors

| Provider | Purpose |
| -- | -- |
| Railway | Compute and hosting |
| Neon | Postgres database |
| OpenRouter | LLM routing |
| Langfuse | LLM observability |
| BetterStack | Logging and monitoring |

## LLM calls

* Only triggered when you use the chat interface
* Query and retrieved context are sent via OpenRouter
* OpenRouter operates a no-store, no-train policy — your data is not retained or used for model training after the response is returned
* Raw repo content is not sent to the LLM

## What we don't do

* We don't use your data for model training
* We don't share data across tenants or with third parties
* We don't ingest anything you haven't explicitly connected

## Certifications

* SOC2 and ISO27001 are on the roadmap
* Our infrastructure sub-processors (Railway, Neon) carry their own compliance posture

### Intellectual honesty (draft vs product)

The Linear draft said *“Raw repo content is not sent to the LLM”*. Your own [ingestion doc](<apps/docs/content/docs/(guide)/connections/ingestion.mdx>) describes **LLM-assisted graph extraction** during ingestion. Stating “never” would be **misleading**. The new page therefore splits **chat** (message + retrieved snippets/context) from **ingestion** (extraction pipeline) and links to ingestion for detail.

### Retention / in-code evidence

There is **no** clear, customer-facing “we retain index data for N days” in the codebase. The page says that plainly and points people to **Get in touch** for deletion/DPA specifics. It only mentions **short-lived auth flows** (password reset, invitations) as operational expiries, not as org data retention policy.

### OpenRouter

The draft’s “no-store, no-train” line is **vendor-specific**; the page links to [**https://openrouter.ai/privacy**](<https://openrouter.ai/privacy>) and [**https://openrouter.ai/docs/features/privacy-and-logging**](<https://openrouter.ai/docs/features/privacy-and-logging>) instead of inventing a dead URL.
