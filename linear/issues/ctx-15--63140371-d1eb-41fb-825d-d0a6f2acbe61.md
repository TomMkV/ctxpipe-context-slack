# CTX-15: Code snippets not accessible in UI

Code snippets in the UI can't be copied or downloaded in the chat UI.

When the user is chatting with the ctxadvisor agent in the UI, the supplied code snippets are not copyable or downloadable.

Additionally, the loading skeleton-UI treatment is not styled correctly - as it is very narrow and looks awkward.

## Comments

### 2026-04-14T08:01:40.980Z · cursor

[**Code snippets UI issues**](<https://www.cursor.com/agents/bc-bc5c3f77-53b3-4cf7-9aaf-9bdce1697966>)

Here is what was wrong and what we changed.

### 1\. Buttons not on the same line as the language label

Streamdown lays out code blocks as **column flex** and puts the actions in a **sticky** strip with `-mt-10`, so the label sits on one row and the buttons on another (your first screenshot).

**Fix:** Scoped overrides under `.ctx-streamdown` turn `[data-streamdown="code-block"]` into a **two-column grid**: column 1 = language header, column 2 = actions, row 2 = the highlighted body across both columns. The sticky wrapper is forced to `position: static` and **no negative margin**, so the toolbar is a single logical row.

### 2\. No hover / not clickable

Two separate problems:

* `isAnimating` defaults to `false` in context, but we now pass `isAnimating={false}` explicitly on `Streamdown` in `MessageResponse` so a future prop merge cannot leave code actions disabled during streaming (Streamdown wires `disabled={isAnimating}` on those buttons).
* The library wraps actions in `pointer-events-none` with `pointer-events-auto` only on the inner strip. If anything in the stacking context misbehaved, clicks could still miss. We set `pointer-events: auto !important` on that wrapper in our override so the strip reliably receives clicks.

**Hover:** Native Streamdown controls are plain `<button>`s without your `Button` variants, so we added `.ctx-streamdown …:hover` rules for the copy/download `data-streamdown` selectors.

### 3\. Awkward streaming “skeleton”

Replaced the fake skeleton lines with a **small circular “avatar”** (reusing `ctx-indexing-dot`) plus `ctx|` and **“Thinking…”**—closer to your second screenshot and less like a bogus message.

### 2026-04-14T07:28:47.256Z · cursor

[**Code snippets UI issues**](<https://www.cursor.com/agents/bc-bc5c3f77-53b3-4cf7-9aaf-9bdce1697966>)

## What was going wrong

Streamdown puts code block **copy** and **download** in a **sticky** toolbar with a **negative top margin** so it sits along the top of the block. `MessageContent` had `overflow-hidden` on every message, so for assistant messages that toolbar was drawn **outside the clipped box** and never appeared—so it looked like snippets “weren’t copyable or downloadable” when the real issue was **UI clipping**, not the clipboard or Streamdown being disabled.

**Assumption to keep honest:** if copy still failed in some browsers after this, the next place to look would be **secure context / clipboard permissions** (Streamdown uses `navigator.clipboard`). The clipping issue is the one we can prove from their layout/CSS.

## What we changed

1. `MessageContent` (`apps/ui/src/components/ai-elements/message.tsx`): keep `overflow-hidden` only for **user** bubbles; use `overflow-visible` for **assistant** content so sticky code actions aren’t clipped.
2. **Streaming skeleton** (`apps/ui/src/features/chat/ConversationThread.tsx`): replace `w-fit` (which shrank to the three dots) with `w-full` and add a few **line-shaped** pulse bars so the placeholder reads like a normal-width assistant reply.

Tests: `pnpm --filter @ctxpipe/ui test` passes.
