You’re right to separate the two concerns:

### What was off before

The first change treated **CTX-94** as a **knowledge graph “Updated …”** display issue by pulling `lastUpdatedAt` from Postgres. That’s orthogonal to **whether a push actually drives partial re-index + scoped ingestion**. I’ve **reverted** that KG/API change and **removed** `knowledgeGraphSnapshot.integration.test.ts`.

### How push → partial ingestion actually works in this repo

1. **GitHub** `POST /api/v1/webhook/github` with `push` → enqueues **repository-ingestion** (after HMAC + DB lookup).
2. The worker runs the **code-ingestion graph**. The **first node** is `reindex` in `reindex.ts`: it `POST`s to codesearch at  
   `CODESEARCH_URL` + `/${repositoryId}/index`  
   with `{ githubToken, targetHash, fromHash }` — `fromHash` is the previous `lastIngestedHash` from the DB.
3. **Codesearch** answers with JSON including `ingestMode: "full" | "partial"` and `changedPaths` / `deletedPaths`. The rest of the graph uses `ingestMode === "partial"` and those paths to **limit** what gets extracted (the “partial ingest from diff” behavior lives there, not in the webhook handler itself).

So “partial ingestion” is **not** something the webhook computes; it’s **codesearch + the ingestion graph** after the job runs.

### What the new test actually guarantees

I added `reindex.codesearch.test.ts`, which:

* Mocks `getInstallationToken` and `fetch` (no real GitHub App, no real codesearch process).
* Calls the real `reindex()` node inside `withLogger`.
* Asserts the **same HTTP contract** as production: URL, `POST` body with `fromHash` + `targetHash` + token, auth header, and that a **partial** response is **merged into state** (`ingestMode: "partial"`, `changedPaths`, etc.).

That is the right layer to lock **“when codesearch returns a partial index, the backend state reflects it”** — which is the prerequisite for downstream partial extraction.

**What it does not do (and can’t, in a fast unit test):** run the **OpenWorkflow** worker, a real **codesearch** container, or the **LLM** end-to-end. A “100% e2e push → partial ingest finished” would be a **separate** long-running or Docker-based test.

### What stayed from the branch

* `github.webhook.integration.test.ts`: with Postgres up, it still checks a **signed** push to `/api/v1/webhook/github` and that the **repo row** goes to “re-indexing” (enqueue path). It does **not** by itself prove partial diffs; the new `reindex` test targets that contract.

PR **#139** is updated with this story and the revert. If you want the next step to be a **true e2e** (webhook + worker + fake codesearch HTTP server in one test process), say so and we can scope that as a follow-up.

## What was wrong (CTX-94)

The knowledge graph screen shows **“Updated …”** from `metrics.lastUpdatedAt` when it exists; otherwise it uses the **max** `lastObservedAt` in the returned edge list (a **limited** query). The API always sent `lastUpdatedAt: null`, so on large/truncated graphs the **sample** could miss newer edges and the label stayed on an old date (e.g. 22 Apr) even after pushes and re-indexing.

## What we changed

* `getKnowledgeGraphSnapshot` now sets `metrics.lastUpdatedAt` to the **latest** `repositories.updated_at` in the org (indexed query on Postgres, not a graph scan). That column is touched when a push webhook runs `markRepositoryIndexingPending` and again when ingestion finishes.
* Added `getMaxRepositoryUpdatedAtInOrg` in `repositories` model.

## Tests

* `knowledgeGraphSnapshot.integration.test.ts`: mocks the **graph driver** (no Falkor), uses real Postgres when available; asserts `metrics.lastUpdatedAt` reflects the repo row, not stale edge timestamps.
* `github.webhook.integration.test.ts`: **same HTTP contract as GitHub** (HMAC-signed `POST`, `x-github-event: push`), seeded DB, **OpenWorkflow stubbed** (stands in for the LLM/codesearch pipeline); asserts the repository is marked `indexReady: false`, `indexingReason: "push"`, and `updated_at` moves forward.

Integration tests **skip** if `DATABASE_URL` is missing or Postgres is unreachable (and **MCP conformance** + **retraction** integration are skipped the same way so the suite stays green without Docker).
