# CTX-110: Invalid AI SDK stream sequence

The chat client is receiving an invalid AI SDK UI stream sequence:

`text-end(id)` arrives without a prior matching `text-start(id)`.

The reported ID, `gen-1779258149-JKCU23nzgbXiWMotz6jt`, looks like a generated model message part ID, not a KG UI object. So this is a **stream protocol integrity bug**, not a graph rendering bug.

## **Likely Cause**

The backend streams LangGraph output through `@ai-sdk/langchain` into AI SDK UI chunks. Internal graph nodes like planner/naming are filtered out:

* `apps/backend/src/domain/conversations/internalNodeMessageFilter.ts`
* `apps/backend/src/domain/conversations/transport.ts`

If filtering drops a `text-start` chunk but allows a later `text-end` chunk for the same ID through, the frontend `useChat` parser throws.

The repo already acknowledges this exact failure mode via:

`apps/backend/src/domain/conversations/uiMessageStreamTextStartRepair.ts`

So the system knows this can happen.

## **Why It May Appear In KG Ask**

KG Ask uses the same chat transport:

`apps/ui/src/features/knowledge-graph/KnowledgeGraphAskPanel.tsx`

The KG UI changes probably did not introduce the stream bug directly. But KG Ask may send richer prompts or selection context, causing the backend graph to take a path where internal LangGraph nodes stream more chunks, exposing the existing bug.

## **Where To Solve**

Best place: backend stream pipeline, immediately before returning the stream response.

In `apps/backend/src/domain/conversations/transport.ts`, ensure `createTextStartRepairTransform()` is the **last transform** before:

`createUIMessageStreamResponse({ stream })`

Current risk: repair happens before later `flushTransforms`. If any later transform emits or reorders UI chunks, repair cannot heal it.

## **Fix Ideas**

1. **Move text-start repair to the end** Apply tool repair and enhancer transforms first, then run `createTextStartRepairTransform()` last.
2. **Strengthen the repair transform** It currently handles `text-delta` and `text-end`. Confirm it also handles any newer AI SDK text chunk variants if the SDK changed.
3. **Add stream invariant tests** Add a test where a later transform emits `text-end` without `text-start`, and assert the final pipeline repairs it.
4. **Log malformed repairs** When the repair transform synthesises `text-start`, emit structured debug/warn logging with chunk ID and source, so we can see whether this is planner, naming, or final agent.
5. **Review internal node filtering** Instead of filtering individual `messages` chunks after they are produced, avoid streaming internal nodes at source if LangGraph supports that cleanly. Filtering post-hoc is fragile.

My strongest recommendation: **move** `createTextStartRepairTransform()` to the final position and add a regression test around the full transport transform order.

## Summary

Resolved **CTX-110** by fixing the conversation UI stream pipeline order.

### Root cause

`createTextStartRepairTransform()` ran **before** enhancer `flushTransforms`. Anything those later transforms emitted (or any chunk that slipped through after repair) could reach the client as `text-end` without a matching `text-start`—exactly what `useChat` rejects.

### Changes

1. **Pipeline order** — Tool repair → flush transforms → **text-start repair last** (via new `pipeConversationUiStreamTransforms()` in `conversationUiStreamPipeline.ts`).
2. **Regression tests** — `transport.test.ts` proves a flush transform that emits `text-end` alone gets repaired; `uiMessageStreamTextStartRepair.test.ts` covers the bare `text-end` case from the issue.
3. **Observability** — Structured `warn` when a synthetic `text-start` is inserted (`conversation.ui_stream.text_start_repair`).

### PR

Draft PR: [https://github.com/ctxpipe-ai/ctxpipe/pull/183](<https://github.com/ctxpipe-ai/ctxpipe/pull/183>)

The existing repair logic already handled `text-delta` and `text-end`; the bug was **when** it ran, not **what** it repaired. Moving it to the final position matches the issue’s strongest recommendation and closes the gap where post-repair transforms could break stream invariants again.
