# CTX-64: Dashboard data for realtime stats

A dashboard showing usage would be good. Something to evidence the usage of the agent fleet vision - however we would need additional data points for it.

---

Some examples:

1. An mcp_invocations Postgres table with:

* id, orgId, userId, toolName, invokedAt (indexed DESC), durationMs, success, errorCode
* repositoryId? — only if the MCP tool call carries one (not all do today)
* Maybe sessionId if you want to group calls within a single MCP session

 2. MCP server instrumentation — apps/backend/src/mcp/tools.ts currently emits to Amplitude + OTEL but doesn't write to Postgres. Need a tool-call wrapper that inserts a row on every invocation. userId + orgId are already in scope via withBearerAuth, so identity is free; toolName / durationMs / success come from the wrapper.
 3. Repo linkage decision — for per-repo signal, MCP tool inputs need to carry repoId (or a resolvable path → id lookup). Audit which tools have repocontext today. If most don't, per-repo is a separate follow-up.
 4. A daily rollup — either a Postgres mcp_invocations_daily aggregate table refreshed hourly (cron) or a materialized view. Necessary because the heatmap query is COUNT(\*) GROUP BY date_trunc('day', invokedAt) over potentially millions of rows — you don't want that on the hot path. Also keeps the raw table prunable (e.g. drop rows older than 90 d, keep daily rollup forever).
 5. PII / privacy policy — logging per-call metadata is safe; logging tool arguments (search queries, prompts) can leak sensitive code/data. Decide early whether args are stored, hashed, or dropped. Also whether the raw table is org-admin-only or visible to all members.
 6. Write-path performance — on every MCP tool call you're adding one INSERT. Usually fine, but if tool volume spikes consider a pg_notify / Postgres LISTEN-NOTIFY or async batch writer so a slow DB can't slow down the MCP response.
 7. Dashboard API routes under /api/v1/dashboard — /activity/daily, /leaderboard, /feed. Probably as a single dashboard.ts route module.
 8. Live feed transport — polling every \~10 s is the simplest path (what we discussed). True live-push needs SSE or WebSocket wired through the backend. Start with polling; upgrade only if it feels laggy.
 9. Drizzle migration + schema file under apps/backend/src/db/schema/.
10. Backfill acknowledgement — from the first deploy forward only. The heatmap will show "collecting…" gaps for the first few weeks; fine, just make sure the empty state isn't confusing.

Optional but high-value:

* A small trpc-free utility to emit the same event to both Amplitude and the new Postgres table from one call site, so they don't drift.
* eventType column on mcp_invocations (not just toolName) so we can capture non-tool events too (session start, auth, errors). Pick any to drop — a minimal viable set is 1 + 2 + 7 + 9 (no rollup, no repo, no PII policy yet, polling-based feed). That'd give honest per-user / per-day counts and a live feed from day one of deploy.
