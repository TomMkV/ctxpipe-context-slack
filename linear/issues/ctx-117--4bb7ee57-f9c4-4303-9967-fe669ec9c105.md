# CTX-117: Repository delete endpoint times out with `524` in production ( `DELETE /api/v1/repositories/:id` )

### **Issue**

Deleting a repository is failing in production due to request timeout at the edge.

**Observed in browser console**

* `DELETE https://app.ctxpipe.ai/ctx-tev/api/v1/repositories/repo_ago25k3gh5yivikj2ccgy2t3em 524`

A `524` means the request reached origin but origin did not return in time. This points to slow or blocked backend work on repository deletion/unindex, not a frontend-only bug.

### **Environment**

* Host: `app.ctxpipe.ai`
* Tenant/path prefix: `ctx-tev`
* Endpoint: `DELETE /api/v1/repositories/:repoId`
* Repo example: `repo_ago25k3gh5yivikj2ccgy2t3em`

### **Impact**

* Users cannot reliably delete/unindex repositories.
* UI experience is poor (eventual timeout, weak error feedback).
* Risk of unknown state if backend continues work after client timeout.

### **Potential Causes**

1. Delete/unindex is implemented as synchronous long-running work in-request.
2. DB/search/index operations are slow, blocked, or retrying.
3. Connection instability to Postgres or other backing services.
4. Edge/origin timeout budget is lower than worst-case delete duration.
5. Missing cancellation/idempotency handling for retried deletes.

### **Areas to Explore**

* Instrument `DELETE /api/v1/repositories/:id` with stage timings:
  * auth/lookup
  * DB delete phases
  * search/index cleanup
  * final commit/response
* Correlate failures with DB logs (long queries, locks, reconnects, restarts).
* Confirm whether delete continues after `524` (and whether retries are safe).
* Review proxy/origin timeout settings and upstream connection limits.
* Improve UI mutation handling to show explicit timeout/failure state.

### **Recommended Fix Direction**

Move deletion/unindex to an async job workflow:

* `POST /repositories/:id/delete` (or `/unindex`) returns `202` + `jobId`.
* Worker performs cleanup in bounded batches with retry policy.
* UI shows queued/running/success/failure via polling or events.
* Enforce idempotency key/guard for repeated requests.

### **Acceptance Criteria**

* Deleting/unindexing a repository no longer depends on a single long-lived HTTP request.
* No `524` on normal delete operations.
* UI always shows deterministic status and errors.
* Operation is idempotent and safe to retry.
* Logs expose per-phase timing and root-cause-friendly diagnostics.

### 2026-05-25T06:56:53.272Z · cursor

[**Async repository deletion**](<https://www.cursor.com/agents/bc-31bf718c-84da-4afd-bf27-2d54a640254f>)

I fixed **CTX-117** by moving repository deletion off the synchronous HTTP path. The root cause was real: `DELETE /api/v1/repositories/:id` ran the full cleanup in-request (`purgeRepositoryEvidencePg`, graph sync, FalkorDB, codesearch), which can exceed Cloudflare’s origin timeout and surface as **524**.

## What changed

**Backend**

* New OpenWorkflow: `repository-deletion` — runs existing `deleteRepositoryWithCleanup` in the worker.
* `DELETE` now returns `202 Accepted` with `{ jobId, status: "queued", repositoryId }` instead of waiting for cleanup.
* Repo row is marked `indexingReason: "deleting"` before enqueue so the UI has durable state.
* **Idempotency**: `idempotencyKey` = `repository-deletion:{orgId}:{repositoryId}` (safe retries).
* **Phase timing logs** on lookup, Postgres, graph sync, Falkor repo node, and codesearch.

**UI**

* Accepts `202`, shows **deleting**, polls the repository list every 3s while any repo is indexing or deleting.
* Toast: “Unindexing repository — this may take a minute” (sets expectations).

**Docs**

* Unindex guide updated for async `202` behaviour.

## PR

Draft PR: [https://github.com/ctxpipe-ai/ctxpipe/pull/200](<https://github.com/ctxpipe-ai/ctxpipe/pull/200>)

## Caveats (worth being honest about)

1. **Worker must be running** — if the OpenWorkflow worker is down, deletes stay queued; the API still returns quickly, but cleanup won’t finish. That’s the same operational dependency as ingestion.
2. **Not a separate** `POST …/delete` **endpoint** — kept `DELETE` but changed semantics to async `202`, which matches the issue’s direction without breaking the existing route shape.
3. **Ingestion vs deletion race** — if ingestion and deletion overlap on the same repo, behaviour depends on which workflow wins; worth monitoring in production, but it’s an edge case.

If you want a dedicated job-status endpoint (`GET …/deletion-jobs/:jobId`) for explicit polling instead of list-based polling, that can be a follow-up on the same PR or a small second change.
