[**Integration platforms self-hosting**](<https://www.cursor.com/agents/bc-bb8a7a3a-42ee-43e7-b7be-3fef6f252b5d>)

If the goal is **“reliably read from many SaaS/API/DB sources”** and you **own transforms + Git materialization**, you are mainly shopping for an **extraction + orchestration** layer. Practical options fall into a few buckets.

## 1) OSS connector platforms (max prebuilt “read from X”)

**Airbyte (OSS, self-host)**

* **Strength:** Very large connector catalog, UI/ops, incremental modes where the connector supports them, scheduling, retries.
* **Fit:** Best when you want **many sources quickly** and you are fine treating Airbyte as the **extract** stage; you consume its output (files/warehouse/DB/stream) and then run your **TS processing → Git**.
* **Tradeoff:** Connector ecosystem skews **Python/Java**; “everything in TS” usually means TS **after** extract.

**Meltano + Singer taps (OSS, self-host)**

* **Strength:** “Pipelines as code,” lots of community taps, good for repeatable batch/ELT workflows.
* **Fit:** Similar to Airbyte philosophically, often nicer if you want **git-versioned pipeline definitions** and a more engineer-native workflow.
* **Tradeoff:** Still **Python-first** for most taps.

**Apache NiFi (OSS, self-host)**

* **Strength:** Visual flow programming, strong for **routing, throttling, enrichment, many protocols**.
* **Fit:** Organizations that want **ops-controllable** ingestion graphs and lots of edge-case connectivity.
* **Tradeoff:** Heavier operationally; not the fastest “SaaS SaaS SaaS” path unless your team likes NiFi.

## 2) “Library-first” extraction (less platform, more code, still accelerates)

`dlt` (data load tool) / Singer-style incremental patterns

* **Strength:** Incremental loading patterns, schema evolution handling, can be embedded in your services.
* **Fit:** If you want **pipelines in repo** and you accept Python for extract, but keep your product logic elsewhere.

**OpenAPI/SDK generation + shared internal fetch layer (often TS)**

* **Strength:** Best when sources are **REST-heavy** and you care about **type-safety and custom semantics** more than a catalog.
* **Fit:** Fewer connectors “for free,” but often **highest control** and cleanest integration with your **Git writer**.

## 3) Orchestration without pretending it’s “integrations”

**Temporal / Windmill / n8n (self-hostable)**

* **Strength:** Schedules, retries, fan-out, webhook triggers, human-visible runs.
* **Fit:** Great as the **job system** that calls connectors (your code or Airbyte jobs).
* **Tradeoff:** Doesn’t replace building **per-source read logic** unless paired with Airbyte/Meltano/etc.

## 4) Auth/token plumbing (still the hidden multiplier)

Even when you “only read,” you still need **OAuth, refresh, rotation, per-tenant secrets**. Options:

* **Self-host Nango (paid tiers for the pieces you need)** for auth/proxy, while you keep storage/processing/git.
* **Your own token vault + vendor OAuth apps** (more work, zero vendor dependency).

## A sensible decision shortcut

* **Want maximum prebuilt readers soon:** **Airbyte OSS** (or **Meltano**) as the read layer, then your pipeline consumes outputs.
* **Want maximum control + TS-centric:** **internal connector SDK** + **Temporal** (or your existing worker stack) + optional **PyAirbyte** only where it pays for itself.
* **Want “integration graph” ops tooling:** **NiFi** (if your team will actually operate it).

If you share **which source categories dominate** (Atlassian-only vs “10 SaaS REST” vs “lots of SQL/CDC”), the best default usually becomes obvious: **Airbyte/Meltano wins on SaaS breadth**, **SDK+Temporal wins on deep/custom semantics**.

[**Integration platforms self-hosting**](<https://www.cursor.com/agents/bc-bb8a7a3a-42ee-43e7-b7be-3fef6f252b5d>)

There is **no mature, single open-source product** that simultaneously checks all of these boxes the way Nango+Merge+Composio imply for SaaS:

* **self-hosted, no data plane to a vendor**
* **first-class “sync arbitrary SaaS → Git” with incremental updates**
* **first-class “MCP server with OAuth to those same sources”**
* **mostly TypeScript end-to-end**

What exists in the wild is usually **two layers you compose**, plus **one product choice** depending on whether you want “lots of prebuilt extractors” vs “we own the code in TypeScript.”

## 1) Purpose #1 — sync sources → Git (incremental)

**Git as the sink is almost always custom.** OSS ELT stacks optimize for **warehouses / lakes / OLTP** (Postgres, S3, BigQuery), not “commit Markdown/JSON into a repo on every change.” Airbyte’s world is representative: plenty of **sources**, but **“Git destination” is not a standard, maintained primitive** you can rely on like Postgres—people typically **sync to object storage or a DB, then a commit step**, or they write a **small custom destination**.

Practical patterns that respect your constraints:

**A. “All TypeScript, we control everything” (fits ctx| best)**  
Build a thin **connector runtime** in TS:

* **OAuth + token refresh + per-tenant encryption** (you can borrow ideas from Nango’s model without using their cloud; or pay for Nango enterprise self-host if the economics work).
* **Incremental state** (cursors, `updatedSince`, Jira `changelog`, Confluence versions, Slack `ts`, etc.) stored in **your Postgres**.
* **Webhook ingress** + **reconciliation jobs** (missed events).
* **Git publishing** as a dedicated module: clone bare/working tree, write deterministic paths, commit with stable ordering, push via deploy keys or app tokens.

Orchestration/durability (still self-hosted, OSS):

* **Temporal** (self-host): excellent for “sync job workflows, retries, schedules” (workers can be TS).
* **Windmill** (self-host, OSS AGPL): strong if you want **scheduled TS jobs + webhooks + UI** without building as much plumbing (still your code for each vendor).

**B. “Maximize prebuilt extractors; TS at the edges”**

* **Airbyte OSS** (self-host): great **catalog of sources** and operational UI; core connectors skew **Python/Java**. You can stay TS-heavy **outside** Airbyte (trigger runs, post-process, git commit), or use **PyAirbyte** for programmatic extraction if you accept Python in the pipeline.

**C. Singer/Meltano ecosystem**  
Lots of connectors, but it’s **Python-first**—works if you relax “TypeScript everywhere.”

**Bottom line for purpose #1:** the acceleration is less “install one magical integrator” and more **pick an extraction strategy** (custom TS vs Airbyte vs Singer) and **standardize** OAuth, state, webhooks, rate limits, and the **git writer** once.

## 2) Purpose #2 — MCP server with auth (agents access sources)

MCP itself doesn’t solve OAuth multi-tenancy; you implement **transport + session + scopes**.

Good TS building blocks (all self-hostable; data stays on your infra):

* `@modelcontextprotocol/sdk` (official MCP TypeScript SDK) for the server.
* **HTTP streaming transport** behind your normal API gateway + **mTLS/TLS**.
* **Auth**: OAuth 2.1 / bearer tokens validated by **your existing auth** (e.g. Keycloak, Authentik, or your app’s IdP). Community frameworks like **FastMCP** are optional sugar; the core requirement is **token validation + per-tenant credential lookup**.

How MCP should read data (important design choice):

* **Preferred for “synced copy” products:** MCP tools read from the **materialized mirror** (git checkout path, or SQLite/Postgres index), not live-call Slack/Jira on every tool invocation. That keeps MCP fast, rate-limit friendly, and consistent with what you ingested.
* **Optional live tools:** only for actions that truly need freshness, with strict quotas.

## 3) A concrete “ctx|-shaped” reference architecture (meets your constraints)

1. **Ingestion service (TS)**: connectors + webhook receivers + job enqueue.
2. **Worker (TS)**: executes sync slices; persists normalized docs + blob storage if needed.
3. **Git publisher (TS)**: turns snapshots/diffs into commits (idempotent).
4. **MCP server (TS)**: authenticates users/agents; tools query **local mirror**; separate “live action” tools if you must.

That gives you **one tenancy model**, **one credential store**, and **one data path**—without requiring a third-party integration cloud.

## 4) If you want “buy some acceleration” without violating self-host

* **Nango Enterprise self-host** is still the closest “integration-specific accelerator,” but you already noted **free self-host lacks sync functions**—so it’s a **commercial/ops trade**, not an OSS shortcut.
* Otherwise, acceleration mainly comes from **internal codegen + shared libraries** (OpenAPI clients, pagination helpers, webhook verification, retry policies), not from a single OSS analogue to Merge.

---

**Direct answer to your question:** for strict **self-host + no vendor data plane + TS-first + Git sink + MCP**, the realistic path is **compose Temporal or Windmill + your TS connector kit + official MCP SDK**, optionally **Airbyte** if you accept Python for extraction and keep git commits in TS. There isn’t a widely adopted OSS “Nango-with-syncs-but-free” equivalent that also covers MCP auth end-to-end.

If you tell me whether you’d accept **Python-only inside Airbyte workers** (TS everywhere else), I can narrow this to a single recommended default for ctx|.

This is a **research spike** (CTX-36): no repo changes or PR are needed. Below is a direct comparison with your **self-hosting constraint** and **dev-centric sources** in mind.

## How to read the three products

They sit in **different layers**:

|  | **Primary job** | **What you still own** |
| -- | -- | -- |
| **Nango** | OAuth, token refresh, credential vault, proxy, and **sync jobs** you define (ingestion orchestration). | **Schemas, mapping, business logic,** and usually the **canonical store** for indexed content. |
| **Merge** | **Unified API** + maintained connectors: normalized objects (e.g. ticketing “Ticket”) across vendors. | **Gaps vs your product model**, edge cases, and anything outside their normalized model. |
| **Composio** | **Agent tool layer**: wrapping third-party APIs as tools/MCP for LLMs to call. | **Durable indexing pipelines**, long-horizon sync semantics, and strict tenancy if you need deep control. |

So: **Merge** optimizes “read/write SaaS data with one API shape.” **Nango** optimizes “stop rebuilding OAuth + reliable pipes to each API.” **Composio** optimizes “give agents lots of actions quickly.”

---

## Self-hosting: “no vendor touches our customers’ data”

Interpret this carefully:

* **If you mean “our self-hosted deployment must not depend on a third-party SaaS control plane”**: only **Nango (self-hosted)** fits naturally among these three. You run it; tokens and sync metadata live in **your** Postgres/Redis/object storage on **your** network. Nango documents **free self-hosted** vs **enterprise self-hosted** (full parity with cloud features is an enterprise concern on their side). Enterprise self-hosted products sometimes still **report usage/billing telemetry** to the vendor—worth a explicit legal/infosec review if “zero bytes to vendor” is literal.
* **If you mean “customer content must never transit a vendor network, even encrypted”**: **Merge** and **Composio** are **usually wrong** as the default path. Even with **single-tenant**, **region residency**, or **“store in your DB” (Merge has talked about pushing synced data to customer-owned storage)**, the **integration plane** still tends to be **their** operated infrastructure for auth, transformation, routing, or agent tool execution—unless you negotiate something explicitly air-gapped (Merge: enterprise/VPC-style options may exist; Composio: **VPC / enterprise deployment** is marketed, not a downloadable OSS core).

**Practical takeaway for strict self-host customers:** treat **Nango-style self-host** (or fully in-repo connectors) as the default; treat **Merge/Composio** as **optional for your cloud/SaaS SKU** or **explicit enterprise contracts** with documented data flows, not as “automatically satisfies self-host data sovereignty.”

---

## Dev-related sources (Confluence, Jira, Backstage, PagerDuty, Datadog, …)

### Atlassian (Confluence / Jira)

* **Merge** explicitly targets **Jira** (including **Data Center** in their materials) and **Confluence** under unified categories (e.g. ticketing / knowledge-base style models). This can **shorten time-to-first-read** for standard objects (issues, pages, comments, attachments—subject to their model’s fidelity vs what you need).
* **Nango** won’t remove Atlassian’s product quirks; it helps with **OAuth 2.0(3LO)** / token lifecycle and gives you a place to run **your** sync logic. **Forge + org scoping + lifecycle** is still often **Atlassian-specific work**—a unified API rarely eliminates that whole class of problems.
* **Composio** is more about **agent actions** than being your **canonical ingestion engine** for Confluence.

### Backstage

Typically **Backstage itself is already “self-hosted inside the customer”** (their K8s). Integrations are usually **catalog processors**, **plugins**, and **proxies** to Git/internal APIs—not something these three “replace” wholesale. **Nango** can still help if you need **OAuth to external SaaS** from a plugin running in your product (not necessarily inside their Backstage cluster).

### PagerDuty / Datadog / “ops data”

* **Merge** has been expanding **agent/connector** style surfaces (their docs reference things like **Datadog** and **PagerDuty** connectors in agent-oriented docs). That’s closer to **tooling for agents/workflows** than a classic “unified CRM API,” so evaluate it against **your** needs: incidents, dashboards, monitors, SLOs each have different API granularity.
* **Composio** may cover some of these as **tools**, but again: **data path + compliance** must be validated for self-host.
* **Nango**: you implement the **Datadog/PagerDuty REST** behavior you care about; Nango carries **auth + scheduling + retries**.

### Databases / Prometheus / Grafana / MSSQL

These are **poor fits** for “unified SaaS API” vendors:

* **MSSQL / Prometheus / Grafana** are commonly integrated via **direct drivers**, **OpenTelemetry**, **remote-read/write**, or **OSS ETL** (Airbyte/Meltano, etc.), not Merge-style unified models.
* **Nango** is only relevant where there’s an **OAuth/service account** SaaS-style boundary—not for raw SQL wire protocols.

---

## Other ways to accelerate coverage (beyond these three)

1. **Tier your integration strategy**
   * **Tier A (high leverage, many customers):** invest in first-party depth (Slack, GitHub, Jira, Confluence, Google).
   * **Tier B:** “good enough” read-only ingestion via **standard APIs + shared internal SDK** (pagination, rate limits, webhooks).
   * **Tier C:** community connectors / slower roadmap.
2. **Internal platform: “connector kit”**  
   One library for **OAuth**, **webhook verification**, **cursor-based sync**, **idempotent writes**, **encrypted token storage**, **per-tenant rate limits**—then each connector is mostly **mapping + tests**. That’s where **Nango** either **accelerates** or **inspires** your design.
3. **ETL for analytical copies**  
   For “copy data to warehouse / reindex,” consider **OSS ELT** stacks where self-host is native, separate from the “agent tools” problem.
4. **Webhook-first + lazy backfill**  
   For many SaaS sources, **80% of freshness** is webhooks; **full history** is a one-time job. A platform choice matters less than this pattern.

---

## Recommendation framed for ctx|

* **Strict self-host / zero vendor data plane:** default to **self-hosted Nango** *or* **in-house connector runtime**; use **direct vendor APIs** for ops tools and databases.
* **Hosted/SaaS ctx| where customers accept a subprocessors story:** **Merge** can speed **normalized SaaS reads** (especially ticketing/knowledge) if their object model matches your product; **Composio** can speed **agent breadth** if you accept their execution/trust boundary.
* **Atlassian in particular:** expect **ongoing Forge/OAuth/site-model work** regardless; a unified API **reduces** some REST drudgery but **does not erase** Atlassian platform constraints.

## CTX-36 — Nango vs Merge vs Composio (and how to actually go faster)

### What you are optimising for (two different problems)

1. **Product integrations** — each customer connects *their* Slack/Jira/Notion; you need OAuth, token refresh, tenancy, rate limits, and often **incremental sync** (webhooks + backfill).
2. **Agent/tool calling** — an LLM invokes discrete actions (post message, create ticket) with short-lived context; volume and correctness constraints differ from durable indexing pipelines.

The Confluence/Forge work sits in bucket (1) and is unusually heavy because **Atlassian pushes lifecycle and tenancy into Forge/installation models**, not plain REST+OAuth. No generic “unified API” removes that entirely.

---

### Nango ([nango.dev](<https://nango.dev>))

**What it is:** Infrastructure for **auth + connections + pulling from many APIs**, with a path toward **your own** unified models (they document unified-API patterns; you still own schema mapping for non-trivial products).

**Where it helps you:** Strong fit for **“stop rewriting OAuth 2.0 and token storage per vendor”** and for **proxying requests** through managed credentials. That directly attacks weeks of boilerplate *if* the remaining work is REST pagination, not Forge.

**Where it does not help:** It does not magically give you **one data model** across Slack, Jira, and Google Drive. You still design ingestion, idempotency, and **change detection** per source (or you accept thin wrappers only).

**Verdict:** **Most viable of the three as a shared integration layer** for a product like yours that needs many OAuth SaaS connections and server-side sync — especially as an interim acceleration while you harden your own connector framework.

---

### Merge ([merge.dev](<https://merge.dev>))

**What it is:** A **category-specific unified API** (historically HRIS / accounting / CRM-style domains). One Merge “integration” normalises *similar* systems in one domain.

**Where it helps:** If ctx| eventually sells “CRM view” or “ticketing view” with a **small set of canonical entities**, Merge-class vendors can slash time inside that category.

**Where it does not help:** Your list mixes **comms, docs, PM, support, files, metrics, SQL** — Merge is not a single abstraction for that whole surface. You would still build many bespoke connectors; you might also hit **per-linked-account pricing** that scales with every customer × every system ([merge.dev/pricing](<https://merge.dev/pricing>)).

**Verdict:** **Useful for a subset of roadmap** (e.g. CRM/ticketing if they align with Merge’s categories), **not** a blanket accelerator for the full matrix.

---

### Composio ([composio.dev](<https://composio.dev>))

**What it is:** **Agent-native** toolkits: managed auth + tool definitions + routing for LLMs (many frameworks supported). Optimised for **“model calls tool X”**, not necessarily for **“index entire Confluence space under org tenancy with reliable replay”**.

**Where it helps:** Prototyping agent actions across many SaaS APIs, demos, or **narrow** automation paths without owning every OAuth app registration detail upfront.

**Where it does not help:** Bulk historical ingest, strict **data residency**, custom **webhook semantics**, and **first-class indexing pipelines** are still largely yours. Composio can complement agents; it is a weak substitute for a **sync engine** unless you deliberately architect around it.

**Verdict:** **Good short-term for agent surfaces**, **weak as the core platform** for durable, org-scoped knowledge ingestion unless you explicitly narrow scope to agent-mediated access.

---

### Skeptical read of the underlying assumption

The assumption “surely a common pattern means one vendor solves it” understates **variance**:

* **Auth** is somewhat standardisable (Nango-class tools win here).
* **Semantics** (what is a “document”, how deletes propagate, how permissions map to your graph) are **not** standard — unified APIs only help where vendors are **homogeneous within a category**.

So the honest answer is: **you can accelerate OAuth and HTTP plumbing; you cannot buy away domain-specific ingestion design.**

---

### Other ways to accelerate coverage (often higher leverage than picking one vendor)

| Approach | Role |
| -- | -- |
| **Internal connector kit** | One interface: auth handle, `fullSync`, `deltaSince`, `webhook`, `normalize → internal event`. Nango (or similar) plugs into the auth slot. |
| **Webhook-first, poll-second** | Ship “good enough” depth per tool faster; defer perfect backfill. |
| **ELT / CDC tools** | **MSSQL** and some operational stores: **Airbyte / Fivetran / native CDC** often beat “SaaS integration platforms”. **Prometheus/Grafana** are usually **ops-owned** endpoints (remote read, alerts API) — rarely via Merge-style products. |
| **Buy depth in one category** | e.g. Merge (or competitor) **only** where unified CRM/tickets truly match the product. |
| **Defer exotic sources** | File exports, MCP servers maintained by vendors, or read-only SCIM/OIDC for identity — depending on product needs. |

---

### Practical recommendation for ctx|

1. **Short term:** Evaluate **Nango** (or equivalent: embedded auth + connection vault + proxy) as the **shared auth and HTTP layer** behind *your* connector interfaces — aligns with your existing direction (e.g. Atlassian webhooks in `apps/backend`) without pretending one vendor models all tools.
2. **Parallel:** Use **Composio** (or narrow MCP toolkits) only where **agents** need breadth quickly, not as the canonical ingestion bus.
3. **Selective:** Consider **Merge** only after you **name 1–2 canonical domains** (e.g. “CRM deals” or “HRIS employees”) where unified APIs genuinely reduce product surface — not for “everything on the list”.
4. **Keep Forge/Confluence-class work** in the “unavoidable custom” bucket; compare Nango to **reducing duplicate OAuth/sync scaffolding** for Slack, Notion, Linear, etc., not replacing Forge.
