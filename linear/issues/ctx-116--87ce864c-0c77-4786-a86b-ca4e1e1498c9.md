# CTX-116: Auth session lookups failing with intermittent Postgres connection termination ( `INTERNAL_SERVER_ERROR` )

### **ssue**

We are seeing intermittent auth failures from Better Auth during session token validation.
The failing path is a standard session lookup query against `sessions` by `token`, but the DB connection is dropping during execution.

**Observed error chain**

* Better Auth: `INTERNAL_SERVER_ERROR`
* Drizzle: failed query on `sessions` by token
* `pg-pool`: `Connection terminated unexpectedly`

### **Impact**

* Users may be randomly signed out or unable to authenticate.
* Session validation reliability is degraded.
* Potentially increased error rate on authenticated API routes.

### **Evidence**

* Query is valid and routine:
  * `select ... from "sessions" where "sessions"."token" = $1`
* Failure occurs in connection/pool layer, not query semantics.
* Runtime warning indicates SSL mode ambiguity in connection string handling (`pg-connection-string` deprecation warning).

### **Potential Causes**

1. **Postgres availability blip**
   Database restart/failover or provider-side connection reset at time of request.
2. **Network instability between app and DB**
   Transient transport interruption causing socket termination.
3. **SSL/TLS configuration mismatch**
   `sslmode` semantics may not align with cert/hostname setup, causing intermittent handshake/validation failures.
4. **Pool-level behaviour under load**
   Pool exhaustion, stale/idle connections, or aggressive timeout settings resulting in abrupt termination.
5. **Proxy/infra idle connection recycling**
   Upstream proxy/load balancer closing long-lived DB connections unexpectedly.

### **Areas to Explore**

* Correlate app error timestamps with DB/provider events (restart, failover, dropped connections).
* Validate `DATABASE_URL` SSL params and explicitly set intended mode (`verify-full` vs libpq-compatible require behaviour).
* Inspect pool config (`max`, `idleTimeoutMillis`, `connectionTimeoutMillis`, keepalive settings).
* Confirm infra path between app and DB (NAT/proxy/LB idle timeouts, connection reuse behaviour).
* Add instrumentation around DB connect/query lifecycle to distinguish connect-time vs in-query disconnects.
* Audit logging for token exposure (current logs include raw session token in query params); redact/mask sensitive values.

### **Definition of Done**

* Root cause identified with evidence (not guesswork).
* Mitigation shipped (config/code/infra) and validated in staging.
* Auth error rate returns to baseline.
* Sensitive session token values are no longer logged in plaintext.

## CTX-116 — Postgres pool hardening for auth sessions

### Root cause (what the code supports)

The failure pattern (`sessions` lookup → Drizzle → `Connection terminated unexpectedly`) points at the **pool/transport layer**, not query logic. In this repo the main API pool was misaligned with reality:

| Setting | Before (`client.ts`) | Checkpointer pool (already OK) | Typical pooler/LB behaviour |
| -- | -- | -- | -- |
| `idleTimeoutMillis` | **300s** | 30s | Idle cut-off \~30–60s |
| `keepAlive` | off | on | Silent socket death |
| SSL | implicit via URL | — | `sslmode` deprecation warnings |

So the app could reuse connections the server had already dropped — especially on auth `get-session` paths that hit `sessions.token` often.

We cannot prove a specific Neon/Railway incident from code alone; staging/production should correlate auth 500s with pool `db.pool` events after deploy.

### Mitigation shipped

Draft PR: [**https://github.com/ctxpipe-ai/ctxpipe/pull/199**](<https://github.com/ctxpipe-ai/ctxpipe/pull/199>)

1. `createPgPool` **/** `RetryingPgPool` (`apps/backend/src/db/pg-pool.ts`) — keepalive, 30s idle timeout, `maxUses`, explicit TLS from `sslmode` (stripped from the URL to avoid ambiguous re-parsing), pool error logging, **one retry** on transient termination.
2. `sanitizeDbError` — redacts session tokens (and similar) in `DrizzleQueryError` messages before evlog / global `onError`.
3. **Shared factory** for the main DB, migrate script, and LangGraph checkpointer.

### Tests

* 10 new unit tests — all passing.
* Full backend suite still has **pre-existing** failures on `main` (e.g. `app.test.ts` UI proxy / `getSession` expectations); nothing new tied to this change.

### After merge

* Deploy to staging and watch auth error rate vs baseline.
* Ensure production `DATABASE_URL` uses an intentional `sslmode` (`require` for managed TLS without strict hostname verify; `verify-full` when you need strict verification).
