### Why you see `400` on `POST /.auth/api/v1/auth/oauth2/token` but **no explanation in backend logs**

In this codebase, `/.auth/api/v1/auth/*` is delegated straight to Better Auth — no app-owned handler wraps the OAuth2 token route and writes `error_description` into evlog:


OAuth **errors are almost always expressed in the HTTP response**, not thrown as exceptions that your logger would catch globally:

* **Status** `400` (or sometimes `401` depending on endpoint)
* `Content-Type: application/json`
* `{ "error": "...", "error_description": "..." }`

So infra that only indexes `status` + `path` (without **response body** or a **dedicated oauth_token_error** step) will show **many 400s** with **empty or generic** `message`, exactly like your sample JWT error where `message` was `""` in the outer envelope.

Nothing in what we’ve seen guarantees that **Better Auth** (or anything in front of it) **emits structured evlog messages** for `invalid_grant`, `invalid_client`, etc. — so **“missing reason” in backend logs is expected** unless you **add logging** (middleware, proxy capture, or Better Auth hooks) or **log at the edge** (envoy/nginx) with body redaction policy.

---

### What those **400**s usually mean (refresh path)

For `grant_type=refresh_token`, common cases are:

| Situation | Typical OAuth body |
| -- | -- |
| No row for hashed refresh token | `invalid_grant` / `session not found` (Better Auth wording) |
| Refresh expired or revoked | `invalid_grant` / invalid refresh token |
| `client_id` mismatch | `invalid_client` / wrong id |
| Missing / wrong `client_secret` (confidential client) | `invalid_client` |
| Malformed request (body not form-encoded, missing fields) | validation-style 400 |

So **400 on token** lines up with **“refresh flow doesn’t work”** (DB row missing, wrong client, revoked, etc.), while **401 +** `JWTExpired` on `/mcp` lines up with **“still using an expired access token”** (refresh not run yet, failed, or parallel calls with stale Bearer).

* **Capture response body** for `POST .../oauth2/token` in your **reverse proxy / API gateway** (or temporary debug), with **redaction** of `refresh_token`.
* **Reproduce once** with **curl** using the same `client_id` and refresh token from a test client and read the **JSON error**.
* **Correlate by time**: same second as `JWTExpired` on `/mcp` often means **client tried refresh after 401** and got **400** — pair requests by `requestId` if you have it on both.

## 1) Could `oauth_clients` disappear without anyone “resetting the DB”?

There is **no application code under** `apps/backend/src` that deletes OAuth clients or refresh tokens—you only declare the tables and FKs (generated Better Auth schema). So removal happens via **Better Auth’s own OAuth routes**, `DELETE`/maintenance, or `ON DELETE CASCADE`.

* **Cascade from** `oauth_clients` – Your `oauth_refresh_tokens` reference `oauth_clients.client_id` with `onDelete: "cascade"` (same for access tokens / consents). If the **OAuth client row** is deleted, **all dependent refresh-token rows vanish**.

## What failing here actually means

In `@better-auth/oauth-provider`, that specific `error_description: "session not found"` is thrown when `findOne({ model: "oauthRefreshToken", where: [{ field: "token", value: <hashed inbound refresh token> }] })` returns `null`.

So refresh is failing because the server **cannot find a matching row in** `oauth_refresh_tokens` for the refresh token the client sent—not because JWT validation failed and not (at this step) because your app’s `sessions` table is missing a row.

## So why could that happen?

### 1\. **Stale / orphaned client token vs server state (most common in practice)**

The IDE stored a `refresh_token` string, but Postgres no longer has the corresponding **hashed** row. Typical situations:

* **DB reset**, restore, or migrating to another cluster without `oauth_refresh_tokens` (and `oauth_clients`) rows.
* `DATABASE_URL` or environment points the running API at a **different DB** than the one used when the user authorized (wrong deploy, staging vs prod typo, Cursor Cloud secret mismatch, parallel worktrees pointing at different DB names without realizing it).
* `oauth_clients` row dropped → **cascade** deletes refresh tokens (your schema ties refresh tokens to `oauth_clients.client_id` with `onDelete: "cascade"`). Dynamic MCP clients recreated with new IDs **without** migrating old refresh rows also produce “looks like MCP auth works until refresh.”

Nothing here is necessarily a “wrong query”; it’s **state that no longer exists where the refresh handler looks**.

### 2\. **Token rotation semantics**

On refresh, the plugin **revokes the previous refresh token** (`revoked` set) **before** inserting the new row. If the client:

* Calls refresh **twice** with the same refresh token,
* Keeps multiple copies of OAuth state across windows,
* Or **does not persist** the new `refresh_token` from the refresh response,

the second refresh can fail because the stored row no longer applies. That tends to produce **timing/flaky** behavior around expiry.

Again, that’s not a Drizzle typo; it’s **client behavior vs single-use rotation**.

### 3\. **Infrastructure edge cases**

* **Read replicas lagging writes**: theoretically the row exists on primary but reads go to a replica before replication (unusual for small Postgres but possible if you ever introduce HA reader endpoints for the auth DB).
* `AUTH_SECRET` / JWKS issues affect **JWT** access tokens; the `session not found` path is specifically **missing DB row**, not JWKS decryption (different failure modes elsewhere).

### 4\. **Unlikely-but-worth-a-glance adapter/schema mismatches**

If `findOne` silently hit the **wrong table** or **wrong column**, you’d also get “no row.” Your project supplies `oauthRefreshTokens` in the Drizzle schema with `usePlural: true`, which matches Better Auth’s model naming (`oauthRefreshToken` → `oauthRefreshTokens`). That wiring is unlikely to be the bug **if OAuth ever worked once** against the same process; breakage would tend to appear immediately.

## Is it “misconfiguration”?

Often **yes indirectly**: **wrong Postgres**, **lost/cascaded oauth rows**, **stale MCP OAuth state after DB or deploy changes**, rather than `AUTH_BASE_URL` typo specifically. `AUTH_SECRET` churn is emphasized for **JWT/JWKS** issues; for `session not found` on refresh, start with `oauth_refresh_tokens` + client id + DB identity.
