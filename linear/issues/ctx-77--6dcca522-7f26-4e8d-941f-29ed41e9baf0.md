# CTX-77: Add MCP install command for Claude

Railway has this in their docs: 

```
claude mcp add Railway npx @railway/mcp-server
```

It worked immediately in Claude, and felt like a different way of handling adding MCP servers to that agent tool (Claude Code).

Is this something easy to do for us? 

Could we have:

```
Claude mcp add ctxpipe npx @ctxpipe/mcp-server
```

How does this reconcile with our "install MCP via PR" approach? Are these doing the same thing?

I see this as an addition to suit the developers' preference.

With the **stdio +** `npx @ctxpipe/mcp-server` flow as it is implemented today, the user does **not** get an OAuth browser round-trip wired through Claude. Authentication to ctx| is `Bearer` via an API key you put in the environment (we documented `CTXPIPE_API_TOKEN`), created in the product the same way as the existing “API keys + `Authorization` header” MCP path in the docs.

So in practice:

* **Not** “Claude prints an auth link and you click it” as part of the MCP protocol handshake for this bridge (we never hooked up an `OAuthClientProvider` / callback URL flow on the upstream client).
* **Yes** “you already proved who you are to ctx|” by **minting an API key** in **Settings → API Keys** and exporting it for the subprocess env (or whatever mechanism Claude Code uses to inject env into MCP servers).

You *could* design something closer to what you described (e.g. bridge catches OAuth-required, writes an authorisation URL to **stderr**, user opens it, then pastes a code back), but that would be **extra product/engineering work** and is still awkward compared with clients that speak `streamable-http` + OAuth natively. For OAuth-first users, the honest recommendation remains: use the **native remote MCP** config (`streamable-http` + URL) where the client can run the redirect flow, and reserve `npx @ctxpipe/mcp-server` for people who are fine with **API keys** or whose Claude setup can’t do remote OAuth cleanly.

## What I shipped

* Added `packages/mcp-server` (`@ctxpipe/mcp-server`): a **stdio → streamable HTTP** MCP bridge using `@modelcontextprotocol/sdk`. It forwards `tools/list`, `tools/call`, `ping`, and everything else via `fallbackRequestHandler`, so it tracks the real server’s tools without maintaining a duplicate list.
* Wired it into the workspace (`pnpm-lock.yaml`) with a `prepublishOnly` build.
* Extended the MCP guide in `apps/docs/content/docs/(guide)/mcp/mcp-docs.mdx` with `claude mcp add` instructions, env vars, and how that compares to **PR-based** MCP JSON.

Draft PR: [https://github.com/ctxpipe-ai/ctxpipe/pull/128](<https://github.com/ctxpipe-ai/ctxpipe/pull/128>)

## How it lines up with the Linear question

* `claude mcp add … npx …` targets **stdio** subprocesses. ctx|’s product MCP is **streamable HTTP** on the backend, so the Railway-style one-liner is not literally the same transport; the new package is the **thin adapter** so Claude Code gets the same ergonomics.
* It is **the same MCP surface** (same `/mcp` endpoint and tools), not a parallel product. **“Install via PR”** vs `mcp add` is mostly **where config lives** (committed file vs local Claude config); the issue’s “developer preference” framing is accurate.
* **Caveat you should treat seriously**: interactive **OAuth in the browser** does not map cleanly onto a headless stdio child. The docs call out using `CTXPIPE_API_TOKEN` (Bearer) for this path, or sticking to native `streamable-http` when the client can do OAuth properly.

## After merge

Publish `@ctxpipe/mcp-server` to npm from `packages/mcp-server` (or your release pipeline). Until it is published, `npx -y @ctxpipe/mcp-server` will not resolve for end users.

Suggested command (note the `--` before `npx`, which many Claude Code versions require):

```bash
CTXPIPE_ORG_SLUG=your-org claude mcp add ctxpipe -- npx -y @ctxpipe/mcp-server
```
