## RCA (CTX-83)

**Stuck after “Thinking…”**  
The UI loader stays up while `status` is `streaming` but the last assistant message has no renderable parts (`ConversationThread.tsx`). The stream from `POST …/conversations/:id` is built from LangGraph with `streamMode: ["values","messages","custom"]`. `messages` carries LLM tokens from every graph node that calls a model (not only `agent`), and `@ai-sdk/langchain` turns those into UI chunks. A **blocklist** of internal node names is fragile: any chunk whose `langgraph_node` does not match the list still becomes “assistant” traffic in the UI pipeline, which can leave you with reasoning/thinking-style tokens and **no proper final answer** (and no console error if the stream completes “successfully”).

**Duplicate sidebar rows**  
On `/chat` (index), `handleSendMessage` prepends an optimistic `"New Chat"` row, then `invalidateQueries({ queryKey: ["conversations", orgSlug] })` refetches. The server returns the same `id` again; the merge was **prepend without deduping**, so you could see two entries for one conversation.

## What we changed

1. `filterInternalNodeMessageChunks` — switched to an **allowlist**: only forward `messages` events when `metadata.langgraph_node === "agent"`. Other modes (`custom`, etc.) pass through unchanged. Added unit tests: `apps/backend/src/domain/conversations/internalNodeMessageFilter.test.ts`.
2. `ChatWorkspace.tsx` — when applying the optimistic list update, **strip any existing item with the same** `id` before prepending, so refetch + optimistic update cannot duplicate the row.

Railway logs were not available from this environment; the above follows from the streaming pipeline in code and from LangGraph’s `langgraph_node` metadata behaviour.
