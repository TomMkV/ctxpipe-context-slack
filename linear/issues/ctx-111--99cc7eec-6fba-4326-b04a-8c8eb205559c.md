### Fixed / hardened in PR #184

| Issue | Risk | Mitigation added |
| -- | -- | -- |
| `forge lint` without `--environment` | **Blocker** (observed in run 26034271199) | `lint:forge` uses `--environment production` |

`forge deploy --non-interactive` fails with:

```text
Error: --non-interactive requires an analytics setting.
Use forge settings set usage-analytics <value>.
```

`FORGE_DISABLE_ANALYTICS=1` helps for some commands, but the worker explicitly runs `forge settings set usage-analytics false` — that is the reliable fix for deploy.

After lint passes, deploy should reach Atlassian unless auth or permissions fail.

### Remaining risks (operational / design)

**1. Forge credentials (high likelihood if deploy ever ran)**

Both lint and deploy need headless auth:

* `FORGE_EMAIL` — Atlassian account email for the token owner
* `FORGE_API_TOKEN` — scoped Forge API token

Failures look like `Not logged in` or `401` / invalid token. These must live in the GitHub `production` environment secrets and match the account that owns app `4ce198e3-2ce7-4a6e-865f-a3e31d15fe43` in `manifest.yml`.

**2. Deploy permission (medium)**

The token user must be allowed to deploy that app. The backend maps this to `forge_deploy_forbidden`. Wrong account or insufficient Forge/Developer Console access will fail deploy even with valid credentials.

**3. No** `forge install` **in CI (by design, but worth knowing)**

CI only runs `forge deploy`, not `forge install --upgrade`. That matches a **shared reference/marketplace app** (`app.id` is fixed in `manifest.yml`). Per-tenant installs are handled by the **provision worker** (`forge-provision-cli.mjs`: deploy + install to `CONFLUENCE_SITE`).

So CI updates the app bundle; it does **not** push upgrades to every customer site. That is expected if product provision owns installs.

**4. Manifest drift vs backend generator (medium over time)**

`apps/forge-ctxpipe-agent/manifest.yml` must stay aligned with `apps/backend/src/lib/forge-app-manifest.ts` (modules, scopes, routes). The reference manifest uses `${REMOTE_BASE_URL}`; the worker inlines the public API URL. Drift would pass CI lint but break provision or runtime behavior.

**5. pnpm ignored** `@forge/cli` **build scripts (low)**

CI logs show `@forge/cli` postinstall scripts skipped. The `forge` binary still runs from `node_modules/.bin/forge` in testing. Worth watching if CLI behavior regresses after upgrades.

**6. Job ordering (low)**

`forge_deploy` `needs: terraform`. Terraform failures skip Forge entirely (deploy step never ran in the failing run you linked — only lint failed).

**7.** `install:upgrade` **script not CI-safe (low for this workflow)**

```18:18:apps/forge-ctxpipe-agent/package.json
    "install:upgrade": "REMOTE_BASE_URL=https://app.ctxpipe.ai/ forge install --upgrade",
```

Missing `--non-interactive`, `-e production`, and site/product flags. Fine that CI does not call it; risky if someone runs it manually in automation.
