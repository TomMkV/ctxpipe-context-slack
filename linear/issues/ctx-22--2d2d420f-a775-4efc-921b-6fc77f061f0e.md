# CTX-22: Investigate agent's view on ctx|

Please review and determine if this is a reasonable response from the repo-agent based on the evidence provided by ctx| advisor for TruRecAI.

---

Notes from assessing if an in-repo agent (mid context window session - Claude Opus 4.6) had a good impression of the data ctx| provided:

1. I asked Claude in repo 1 (frontend) to learn about repo 2 (backend). As both work together.
2. It searched my filesystem (username/projects) - and drew some conclusions. I queried why it didn't use the MCP, and it said "yeah I should have, but in checking it, it doesn't work" - a seperate bug that's been captured.
3. When it did use ctxadvisor, it found some gaps in the original conclusions:

```
Confirmed:

Better Auth is the org standard (not legacy JWT).
- Next.js rewrites are the mandated proxy pattern — browser must never hit the backend directly.
- Docker Compose is the standard local dev approach.
- Lazy user provisioning: auth service creates the user, backend auto-provisions a local record on first authenticated request.
- Service discovery defaults: backend at localhost:8888, auth at localhost:3456.

New context I missed:
- Vercel is the preferred frontend host (evidenced by @vercel/analytics — I didn't flag this).
- "Fleet pattern" — this platform architecture is being replicated across other repos (lovisa-playground, facecomparison-playground). Consistency matters.
- Lazy sync gotcha — if the backend user provisioning fails, the UI can show an authenticated state but get 404/403 on data fetches. This is a known friction point.
- Dual layout pattern — for Payload CMS integrations, root layout.tsx should return only {children}, with route groups providing their own <html>/<body>. Relevant if Payload CMS gets integrated.
- CORS is a common friction point — CORS_ORIGINS in the backend .env must explicitly include the frontend URL.

Corrections to my earlier analysis:
- I flagged the WebSocket endpoint as potentially missing from the backend. The org context confirms the UI does consume a "TRU Backend WebSocket API" for real-time vision alerts — so that endpoint likely exists and I simply didn't find it in the search. Worth verifying if you hit issues there.
- I was right about the README drift but understated it. The org standard is clearly Better Auth, full stop — the JWT/OAuth2 references in the README aren't just stale, they're misleading.
```

4. I then asked a Cursor (Codex) and Claude Code agents to tell me about the JWT usage in the backend repo, then gave both analyses to the repo 1 agent and asked "what does this tell you?":

```
A few things stand out when you triangulate all three sources:

The ctx_advisor gave a directionally correct narrative but fabricated precision. It cited specific line numbers ("line 344", "line 481") that don't match what either Claude Code or Codex found. Claude Code puts the fallback comment at line 385, create_access_token() at line 219. The ctx_advisor was inventing specifics to support a correct general story — which is a dangerous failure mode because it looks authoritative.

The most important finding the ctx_advisor missed entirely: create_access_token() is dead code. Both Claude Code and Codex independently confirmed it's defined but never called anywhere in the codebase. The ctx_advisor described JWT as a "last-resort fallback" for "legacy clients" and "existing tokens" — implying an active, if deprecated, system. The reality is starker: nothing in the current codebase even creates JWTs anymore. The only scenario where JWT validation fires is if someone presents a token minted by a previous version of the software. That's not "deprecated" — that's dead code with a theoretical backward-compat justification.

The AUTH_ENABLED default mismatch. Codex caught that main.py defaults it to true while docker-compose.yml defaults it to false. The ctx_advisor told me it was false "for development convenience" without flagging the contradiction. That kind of inconsistency between code and compose config is exactly the sort of thing that causes subtle bugs in deployment.

The documentation/script rot is worse than described. auth-helper.sh still comments about "JWT token retrieval" but actually fetches a Better Auth session token. README and docs still reference JWT flows. The ctx_advisor didn't surface any of this drift.

The takeaway for how I should use ctx_advisor: It's useful for organisational intent — what the approved direction is, what the team considers standard. But it shouldn't be trusted for code-level facts. It synthesises a cleaner story than reality warrants. When I need to verify what the code actually does (versus what the org intended it to do), I need to read the source or cross-reference with agents that do. The ctx_advisor is a policy layer, not a code analysis tool — and I should treat it accordingly.
```
