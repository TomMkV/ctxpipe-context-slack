[**Ctx advisor recursion limit**](<https://www.cursor.com/agents/bc-12ebc6c1-9e61-488e-bc79-3b08902c23bb>)

**What the number actually counts**

`recursionLimit` is LangGraph’s **step budget for the inner ReAct graph** (model ↔ tools ↔ middleware), not “number of tool calls.” One user-visible “round” of tools can consume **several** steps, so the same limit supports fewer tool rounds than the raw integer suggests.

**Why 60**

* It’s a **deliberate bump** over the default (\~25) so normal multi-tool `ctx_advisor` turns stop dying with `GraphRecursionError`.
* It’s still **small enough** that a bad loop (model keeps calling tools) fails in **reasonable time/cost** instead of running almost forever.

**Why not 100**

* **100 is also reasonable** if you want more slack for heavy investigations. The choice between 60 and 100 is partly arbitrary; both are “moderate” caps. If traces show you still hit the limit on legitimate long runs, **raising to 100** is a sensible tweak with similar risk profile.

**Why not 500**

* A **single MCP invocation** that needs hundreds of graph steps is usually **pathological** (runaway tool use, repeated searches) or should be **multiple smaller calls** from the client.
* **Cost and latency** scale with steps (LLM + tools); 500 gives a stuck agent a long time to burn tokens before stopping.
* So **500 is a safety/cost tradeoff**: high ceiling, weak guardrail.

**Rule of thumb**

* **60–100**: tighter guardrails, good for “one advisor answer per prompt.”
* **500+**: only if you explicitly want **very long** single-turn agent runs and accept the cost/risk—or you add other limits (max wall time, max tool calls, budget).

If you want alignment with other graphs in the repo (e.g. inner agents using **100–220**), bumping this constant to **100** is consistent and still conservative compared to 500.

## Why the “retrieval pipeline” hits a recursion limit

The failure is almost certainly **not** the linear retrieval graph (`extractQuery` → … → `assemble` → `agent`), which only walks each node once per turn. The limit comes from the **inner LangChain** `createAgent` (ReAct) graph inside `agentNode`: every **model → tools → model** cycle uses multiple LangGraph steps, and LangGraph’s default **recursion budget (\~25)** is easy to exceed when the advisor runs many repo/graph tools in one MCP call. That surfaces as a recursion / `GraphRecursionError` that users describe as the advisor “hitting a recursion limit.”

LangChain’s `ReactAgent` documents passing `recursionLimit` on `invoke` / `stream` for exactly this case.

## Minimal change applied

A constant `AGENT_RECURSION_LIMIT = 60` is passed into `agent.stream()` so normal multi-tool `ctx_advisor` turns stay under the cap without refactoring the agent or retrieval pipeline.

```11:18:apps/backend/src/graphs/conversationGraph/nodes/agent.ts
/**
 * LangGraph step budget for the ReAct tool loop (model → tools → model → …).
 * Default (~25) is easy to exceed when the advisor runs several repo/graph tools;
 * explicit limit avoids GraphRecursionError for typical MCP turns.
 */
const AGENT_RECURSION_LIMIT = 60
```

```100:110:apps/backend/src/graphs/conversationGraph/nodes/agent.ts

    { messages: inputMessages },
    {
      streamMode: "values",
      recursionLimit: AGENT_RECURSION_LIMIT,
      callbacks: langfusePipelineCallbacks({
        step: "conversation.agent",
        dimensions: { source: source ?? "ui" },
      }),
    },
  )
```

* **Optional**: If traces show the limit only on **huge** investigations, bump `60` slightly or add a **single env-backed cap** (operator-tunable) — still a small change.
