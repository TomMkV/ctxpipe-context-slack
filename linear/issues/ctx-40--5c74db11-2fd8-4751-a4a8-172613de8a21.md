Here is the cleaner approach we implemented and how it compares to what you sketched.

### Why this is cleaner than a `signout` special case

Hard-coding `/signout` fixed one typo but did not generalise: any bogus first segment (`/foo/chat/...`, stale bookmark, pasted wrong slug) would still behave like a real org until the API failed. **Gating on membership** matches your mental model: the URL names an org; if you are not in that org, you are out of bounds — no need to infer intent (sign out vs wrong org).

### What we shipped

1. **Removed** `apps/ui/src/routes/signout.$.tsx`.
2. **Added** `apps/ui/src/routes/$orgSlug.tsx` — a layout parent for all `/$orgSlug/*` file routes. It:
   * Waits for `useSession()` and `useListOrganizations()`
   * If signed in and onboarded, checks `organizations.some((o) => o.slug === orgSlug)`
   * If **not** a member → a dedicated page: *“You do not have access to this organisation”* plus short copy and a **Go to home** link (no sign-out, no mystery chat shell)
   * If member → `<Outlet />` as before

TanStack Router’s codegen now nests chat, home, repositories, setup, and org settings **under** this layout (`routeTree.gen.ts` shows `getParentRoute: () => OrgSlugRoute` for those children).

### Caveats (worth being sceptical about)

* **Authorisation is still enforced on the API** — this UI gate is for UX and to avoid pointless client calls. Do not treat it as a security boundary.
* `useListOrganizations()` only reflects orgs the client already knows — if the list were stale or incomplete, a legitimate member could theoretically see the denial screen until a refresh. Same limitation exists anywhere you rely on that hook for navigation.
* **SSR**: the layout runs on the server too; until session/orgs resolve, we return `null` (brief blank). If that flashes annoyingly, a follow-up could add a small skeleton.

PR **#108** is updated on branch `cursor/fix-signout-url-typo-167c` with this approach.

### What was going wrong

The real sign-out URL is `/.auth/sign-out` (with the leading dot). If you hand-edit the path to `/signout/...`, the router no longer matches the auth routes. Instead, it matches `/$orgSlug/chat/$conversationId` and treats `signout` as the organisation slug. Chat then talks to the wrong org, the conversation fetch fails or returns nothing, and you sit in an odd half-loaded state — exactly the “no-man’s land” you saw.

That behaviour is a consequence of using the first URL segment as `orgSlug` everywhere (including `AuthProvider`): any plausible string in that position is interpreted as an org unless you carve out exceptions.

### What we changed

A new splat route `/signout/$` runs `beforeLoad` and `redirect`s straight to `/.auth/sign-out` with `authView: "sign-out"`, so mistyped URLs like  
`https://app.ctxpipe.ai/signout/chat/conv_…`  
land on the real sign-out flow instead of the org chat route.

**Trade-off:** if anyone ever had a real org whose slug was literally `signout`, `/signout/chat/...` would now always redirect to sign-out. That slug would be a poor choice next to this URL scheme anyway; if you need that edge case supported, we would need a different reserved-prefix strategy.
