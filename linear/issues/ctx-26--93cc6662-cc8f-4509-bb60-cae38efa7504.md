# CTX-26: Improve MCP slide in onboarding flow

In the app onboarding flow, there is a slide for the user to get their MCP details, using the previous slide's org-slug in the URL.

This should change to be a panel where the user can select one of two options:

1. Install their MCP manually (like what we have), and
2. Do it automatically (via PR)
   1. User chooses which agents they use (Cursor, Claude, Opencode, etc etc etc)
   2. Shows pre-selected connected repos from previous Connect Github slide - where user can select a subset if they want
   3. Explanation of what will changed via a diff UI
   4. Raise PR(s) (if multiple) with a link
3. It keeps the 'I'll do this later' link

## What I shipped (CTX-26)

**Admin onboarding order** is now: … → **GitHub** → **MCP** → invites, so the MCP step can reference connected repos.

The **MCP slide** is a `McpOnboardingSlide` panel with:

1. **Install manually** — same JSON snippet + copy + Continue as before.
2. **Open PRs for me** — pick **agents** (Cursor → `.cursor/mcp.json`, Claude Code → `.mcp.json`, OpenCode → `opencode.json`), **tick repos** (first page of installation repos, **pre-selected** from saved GitHub setup when URLs line up), **read-only “diff” previews** of what would be written, then **Raise pull requests** (one PR per repo) with links.
3. **I’ll do this later** on the first screen (same idea as GitHub’s skip).

**Backend:** `POST /:orgSlug/api/v1/github/installation/mcp-config-prs` validates `owner/repo` names against the org’s installation, then uses the installation token to branch, add/merge JSON, and open PRs. Helpers + tests live in `apps/backend/src/models/github-mcp-config-pr.ts` (+ `.test.ts`).

## Skeptical notes (worth your scrutiny)

* **Joiner flow** (`welcome` → `overview` → `mcp-config` → `done`) still has no GitHub step; **automatic PRs stay disabled** until they connect GitHub elsewhere. That matches “repos from previous slide” for **admins** only — if you intended joiners to get PRs too, you need an extra GitHub step or copy for them.
* **PR contents** use `AUTH_BASE_URL` for the MCP origin; the **manual snippet** in `onboarding.tsx` is still hard-coded to `https://app.ctxpipe.ai`. If those diverge in self-hosted setups, manual vs PR configs can disagree until you unify them.
* **OpenCode** uses a top-level `mcp` + `type: "remote"` block per their docs; if your users run a different config shape, the PR may need tuning.
* **GitHub permissions**: creating branches/files/PRs needs appropriate **installation** scopes; if installs are read-only, the API will fail with a clear error message.

I ran `vitest` on `github-mcp-config-pr.test.ts` only; full backend `tsc`/vitest in this workspace already had unrelated failures before this change.
