Here is a tighter read of what was going on and what we changed.

## On “422 = wrong payload”

GitHub’s own docs for [Create a reference](<https://docs.github.com/en/rest/git/refs?apiVersion=2022-11-28#create-a-reference>) say **422** means *“Validation failed, or the endpoint has been spammed”* — so it is **not only** “malformed JSON”. A very common case is `sha` not being the current tip of the branch you are branching from (GitHub still returns **422**, often with “Reference update failed” in the message). So treating every 422 as “our POST body is invalid” is too narrow.

That said, we **did** harden the **Git** side of the payload:

* We now resolve the default branch tip with `GET /repos/{owner}/{repo}/git/ref/heads/{defaultBranch}` (`octokit.rest.git.getRef`) and use `object.sha` as the `sha` for `POST .../git/refs`, instead of going via `repos.getBranch` → `commit.sha`. That keeps the `sha` aligned with the same ref namespace `createRef` validates against.
* The existing **retry + backoff** on “Reference update failed” stays, for races where the tip moves between read and create.

## On `localhost:3000` in the modal / PR JSON

That was not the **POST body to our API** being wrong; it was the **MCP URL we embed** in generated JSON:

* The backend used `AUTH_BASE_URL` for `…/mcp?orgSlug=…`. In many deployments `AUTH_BASE_URL` is internal (e.g. `http://localhost:3000` inside Docker) while `CTXPIPE_PUBLIC_APP_URL` is what you already use for the UI build — so PRs and previews showed localhost.

**Fixes:**

1. `MCP_STREAM_BASE_URL` in `apps/backend/src/config/env.ts` (optional URL). `mcpStreamBaseUrlFromEnv(env)` uses it when set, otherwise `AUTH_BASE_URL`.
2. `docker-compose.yml` (backend service):  
   `MCP_STREAM_BASE_URL: ${CTXPIPE_PUBLIC_APP_URL:-}`  
   So when you set `CTXPIPE_PUBLIC_APP_URL` for the UI image, the backend gets the **same public origin** for MCP URLs without duplicating config under a new root env name.
3. `McpConfigPrWizard`: for the **on-screen** “Remote MCP URL” line, the preview now prefers `window.location.origin` in the browser so it tracks whatever host you are actually using (production vs dev), then falls back to `VITE_PUBLIC_API_URL`, then `https://app.ctxpipe.ai`.

Docs/comments were updated in `apps/backend/.env.example` and `docker-compose.env.example`.

## Tests

* `pnpm exec vitest run src/models/github-mcp-config-pr.test.ts` (includes `mcpStreamBaseUrlFromEnv` preferring `MCP_STREAM_BASE_URL`).

All of this is pushed on `cursor/mcp-batch-pr-retry-8d12` (same branch as PR **#107**). I did **not** rewrite the PR description in GitHub so any edits you made there stay intact.

**Deploy note:** ensure production has either `MCP_STREAM_BASE_URL` set explicitly **or** (with Compose) `CTXPIPE_PUBLIC_APP_URL` set so the backend receives the public origin; otherwise it still falls back to `AUTH_BASE_URL`.

## What was going wrong

The error string **"Reference update failed"** with the link to [create a reference](<https://docs.github.com/rest/git/refs#create-a-reference>) is GitHub’s **422** when `createRef` is given a `sha` that is **no longer the tip** of the default branch. With **many repos in one HTTP request**, each repo does several API calls; the default branch can move (other pushes, merges, automation) **after** we read `getBranch` but **before** `git.createRef`. That is a race, not (primarily) duplicate branch names — the repo already had per-repo random branch names.

The `net::ERR_CONNECTION_REFUSED` line in the console is usually **something else** (another request, dev proxy, or the tab losing the server). The **500** on `mcp-config-prs` is the backend returning the GitHub error message from our catch block.

## What we changed

* `createCtxpipeMcpConfigPullRequests` now creates the head ref via `createHeadRefFromDefaultBranch`: on **422** + “reference update failed”, it **waits briefly**, **re-reads** `repos.get` + `repos.getBranch`, and **retries** `createRef` (up to 6 attempts). If the ref name already exists (unlikely), it picks a **new** branch name (up to 4 attempts).
* **UI**: when **more than one** repo is selected, a line under the buttons notes that **batch PRs can take a while** because we call GitHub per repo.
* **Tests**: small unit tests for the Octokit **422** message detection so we do not regress on the string GitHub returns.

Draft PR: [**https://github.com/ctxpipe-ai/ctxpipe/pull/107**](<https://github.com/ctxpipe-ai/ctxpipe/pull/107>) (branch `cursor/mcp-batch-pr-retry-8d12`).

If you still see **connection refused** on the main API URL after this ships, that is worth treating as **infra / URL / proxy** rather than GitHub ref logic — happy to trace that separately if you can capture which exact URL fails in the Network tab.
