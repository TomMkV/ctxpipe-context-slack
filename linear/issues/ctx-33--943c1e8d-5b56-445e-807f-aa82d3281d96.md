# CTX-33: Insufficient context threshold

Where the agent doesn't have enough context, it should refuse a response in a typical manner.

In this example, I chose a repo for indexing but stopped it after 20 seconds. Then I asked about what it thought of the project - which is a simple browser-based RPG.

Where some ingestion issues take place, or is slow, or cancelled - we need some flags in the system prompt or similar to warn the agent from responding with incomplete data or something, otherwise the tool looks like it produces garbage - especially if the consumer didn't do the ingesting and doesn't know.

## What I shipped (CTX-33)

The advisor was getting a long “retrieval context” string but **no explicit signal** that Zoekt/graph coverage was incomplete, so the model could still spin up a believable architecture story. I fixed that in two layers:

1. `CONTEXT_QUALITY_FLAGS` — Prepended to the assembled system message in `assembleNode` so every turn includes machine-readable state: which repos have `index_ready: false`, counts, whether pre-rerank retrieval had any candidates / fleet patterns / hydrated claims in context, and whether `currentProjectName` matches a repository `name` (relevant when MCP passes a friendly name instead of `org/repo`).
2. **Stricter advisor instructions** — In `agent.ts`, added hard rules: when those flags show incomplete indexing or **no** substantive pre-retrieval signal, **do not** characterise a project/repo; give a short refusal, name repos still not ready, and point to finishing indexing or narrowing the question. If everything is marked ready but context is still empty, **use tools** before asserting implementation facts.

Helper + tests: `contextQuality.ts` / `contextQuality.test.ts`.

**PR:** [https://github.com/ctxpipe-ai/ctxpipe/pull/129](<https://github.com/ctxpipe-ai/ctxpipe/pull/129>) (draft)

**Tests run:** `pnpm exec vitest run src/graphs/conversationGraph/contextQuality.test.ts` from `apps/backend`. I did not treat the full backend test suite as a gate here because this environment’s `vitest run` with a path filter still loads suites that need Postgres / `DATABASE_URL`.

## Skeptical note

`index_ready: false` is a **coarse** signal (it means “ingestion never reached the success marker”, not necessarily “user stopped after 20 seconds”). Conversely, if `index_ready` were ever wrong, you still get `pre_retrieval_signal: none` nudging the model toward tools rather than invention — but **wrong** `true` would remain a product/data bug this change does not fix on its own.
