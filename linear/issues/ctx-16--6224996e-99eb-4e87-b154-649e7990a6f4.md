Here is what is going on, without pretending CodeRabbit’s UI is identical in every build.

## What that message actually means

“Failed to complete OAuth authorisation … try entering your access token manually” is almost always **their generic recovery text**: from CodeRabbit’s point of view, the OAuth **handshake did not finish cleanly** (token exchange, storing tokens, or the **first authenticated call** to your MCP URL failed). The product then suggests the **manual** path as a fallback.

That is **not** the same as “you did something wrong by picking OAuth”. OAuth can “look” finished in the browser while **their server** still does not have a valid access token, or has one but **the next request** to your endpoint returns **401** and they map that to this message.

## What “access token” would be (if you ever had to paste one)

It would be the **OAuth access token** their client obtained for your MCP resource — in your stack, that is the **JWT** issued by your auth server for the MCP audience, **not** your GitHub token, not a Linear key, not an API key you create in the ctx| UI.

You are not meant to hunt that down in normal use: a proper MCP+OAuth integration should **store it after the code exchange** and send `Authorization: Bearer <that JWT>` on MCP requests. If their UI does not expose a field when OAuth is selected, that is **their UX gap** (or a bug where the manual path is referenced but not wired for MCP-only OAuth).

## Why there is no way to enter it

Typical reasons:

* **Manual token is tied to another auth mode** (e.g. “API key” or “Bearer token”) and the OAuth-only form **does not show** a paste box — so the copy is misleading.
* **OAuth failed before they persisted anything**, so they never enable the “advanced / manual” panel.

Either way: **you are not missing a secret “ctx| manual token”** — if OAuth completed on their side, you would not paste anything; if it did not, the fix is on **integration or server behaviour**, not on you inventing a token.

## What actually helps on your side

1. **After our backend fix is deployed** (PR that resolves bearer JWTs without `sid`): many “OAuth succeeded then connection failed” cases should **disappear**, because the first MCP call would stop getting **401** for otherwise valid tokens.
2. If it **still** fails after deploy, the next suspects are **issuer/audience mismatch** (`AUTH_BASE_URL` / `AUTH_ISSUER` vs the URL CodeRabbit calls) or **CodeRabbit not sending** `Authorization: Bearer` on MCP — that needs **their** support or logs, not a token you paste from nowhere.

**Bottom line:** the message is a **misleading fallback**; the real problem is “OAuth did not fully succeed from their connector’s perspective or the MCP call was rejected”. It is **not** asking you for a separate mystery token you should know — and if there is no input, their copy is simply poor. Your practical move is **retry after the server fix is live**; if it persists, **open a ticket with CodeRabbit** and ask what HTTP status they get on the post-OAuth MCP request and whether they support your OAuth metadata end-to-end.

## What was going wrong

After OAuth, CodeRabbit calls `/mcp` with a **Bearer** access JWT. Our `withBearerAuth` middleware only loaded `user` / `session` when the JWT included a `sid` (session id). If the token only had `sub` (user id) — which some OAuth/MCP stacks do — verification succeeded, we called `next()` **without** setting the user, and `requireAuth` returned **401**. Many hosts turn that into a vague “enter your access token” step, which matches CTX-16.

IDE clients often still send **cookies** or tokens that include `sid`, so they kept working.

## What we changed

In `withBearerAuth`, when `sid` is missing we now resolve the **latest** `sessions` row for `users.id = payload.sub` and attach that session and user. If `sid` is present but not in the database, we return **401** with `invalid_token` instead of silently continuing.

Relevant logic:

```245:289:apps/backend/src/auth/withAuth.ts
  const db = getSystemDb()
  let tokenSessionContext: { session: AuthSession; user: AuthUser } | undefined

  if (tokenSessionId) {
    const tokenSessionRows = await db
      .select({ session: sessions, user: users })
      .from(sessions)
      .innerJoin(users, eq(sessions.userId, users.id))
      .where(eq(sessions.id, tokenSessionId))
      .limit(1)
    tokenSessionContext = tokenSessionRows[0]
  } else {
    // OAuth access tokens from some MCP clients omit `sid` but still carry `sub`
    // (user id). Resolve the latest DB session for that user so `/mcp` can auth.
    const rows = await db
      .select({ session: sessions, user: users })
      .from(sessions)
      .innerJoin(users, eq(sessions.userId, users.id))
      .where(eq(users.id, payload.sub))
      .orderBy(desc(sessions.updatedAt))
      .limit(1)
    tokenSessionContext = rows[0]
  }

  if (tokenSessionContext) {
    c.set("session", tokenSessionContext.session)
    c.set("user", tokenSessionContext.user)
    return next()
  }

  logBearerAuthFailure(
    new Error(
      tokenSessionId
        ? "Bearer JWT session id not found"
        : "Bearer JWT subject has no resolvable session",
    ),
    { kid },
  )
  return c.json(
    { error: "Unauthorized" },
    401,
    wwwAuthenticateInvalidToken("The access token could not be validated"),
  )
```

The form shows `orgSlug=` with **no value**. Our `/mcp` route returns **400** when `orgSlug` is missing, before auth. CodeRabbit must use a full URL like `https://app.ctxpipe.ai/mcp?orgSlug=your-org-slug`. Worth confirming in the product UI so people do not paste a half-filled template.
