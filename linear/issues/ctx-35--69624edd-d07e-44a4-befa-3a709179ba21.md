# CTX-35: PR merge is not triggering re-index of repo

When a user merges a PR into a connected repo in ctx|, it is not processing a re-index or indexing the diff to update the KG.

The Github app should have a hook we use to get merges or repo changes we use to trigger a re-index - at the very least an index of the diff.

If this reindexing happens, there ideally would be an event we can use to inform the user in the repository page 'indexing recent changes' or 'indexing merge'.

Verified. Short answer: yes, incremental — but the incrementality comes from the already-existing codesearch protocol, not from this PR. This PR just correctly plumbs merge webhooks into that same path.

The diff chain that makes it incremental

1. enqueueRepositoryIngestionWorkflow (new) runs the existing repositoryIngestion workflow.
2. repositoryIngestion passes fromHash: repository.lastIngestedHash ?? undefined and targetHash: resolved.hash into codeIngestionGraph.invoke() (repository-ingestion.ts:183-184, unchanged).
3. The graph's reindex node POSTs {targetHash, fromHash} to codesearch and receives {ingestMode: "full" | "partial", changedPaths, deletedPaths, renames} (nodes/reindex.ts:9-22, unchanged).
4. Downstream nodes short-circuit when state.ingestMode === "partial" — confirmed in embed.ts:21, extractInstructionUnits.ts:452, extractKind.ts:139, identifyAPIs.ts, identifyDatabases.ts, identifyAPIClients.ts, identifyInfrastructure.ts etc. They iterate only scanPaths (the changed set) instead of re-scanning the whole repo.
5. On success, mark-success updates lastIngestedHash = targetHash so the next merge resumes from there.

So:

* First-ever ingestion: fromHash === undefined → codesearch returns ingestMode: "full" → full scan (correct — nothing to diff against).
* Subsequent merges: fromHash is the previously-ingested commit → codesearch returns ingestMode: "partial" with changed/deleted/renamed paths → downstream nodes process only those.
* Edge case (force-push / purged history): codesearch falls back to ingestMode: "full" server-side when it can't compute the diff. Graceful.

## What was actually going wrong

The backend only reacted to `push` on the default branch. That is fine when the GitHub App is subscribed to `push`, but many installs only tick `pull_request` (common for security-focused setups). In that configuration, **merging a PR never hits your handler**, so nothing enqueues `repository-ingestion` and the KG stays stale. Assuming “merge always emits push” is shaky: it depends entirely on which events the installation delivers.

A second issue: `index_ready` stayed `true` for the whole re-ingestion, so the repositories page never showed “indexing …” during updates—only first-time indexing looked “busy”.

## What we shipped

* `pull_request` handling: `action === "closed"` + `merged === true` + base branch equals `repository.default_branch` now enqueues the same ingestion path as a default-branch push, with `indexingReason: "merge"`. Pushes pass `indexingReason: "push"`.
* `repositories.indexing_reason` column + migration; `enqueueRepositoryIngestionWorkflow` sets `index_ready = false` and the reason **before** `ow.runWorkflow`, then clears both on successful completion.
* **REST + UI**: API exposes `indexingReason`; cards show **“indexing merge”** vs **“indexing recent changes”** when not ready.
* **GitHub sync workflow** uses the same enqueue path for newly created repos so the DB pending state is consistent.

PR: [https://github.com/ctxpipe-ai/ctxpipe/pull/114](<https://github.com/ctxpipe-ai/ctxpipe/pull/114>)

**You still need the GitHub App to deliver** `pull_request` (or `push`) to `POST /api/v1/webhook/github`—code cannot fix a subscription that never fires.

**Skeptical note:** If an install has **both** `push` and `pull_request` on the same merge, you may get **two ingestion runs** unless you add dedupe (e.g. by delivery id or a short-lived “last merged SHA” guard). That is a product trade-off we did not optimise in this pass.
